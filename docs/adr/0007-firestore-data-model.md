# 0007: Firestore data model — six collections, listing-bound chat

The data model is six collections with strict ownership boundaries: `members/{uid}` (one per Member Account, self-read-write, Admin sees all), `listings/{id}` (active listings readable by every verified member, writable by the seller), `chats/{id}` + `chats/{id}/messages/{msgId}` (participants only, blocked pairs cannot message), `reports/{id}` (created by any member, **read by Admin only**), `ratings/{id}` (constrained by rules to the two parties of a Sold Listing, one vote per party per deal, per ADR 0004), and `notifications/{id}` (owner-gated, feeding the bell and FCM per ADR 0005).

Two boundary decisions shape it. **Chats are born only from a Listing** — every conversation attaches to exactly one Listing and pairs its seller with one buyer; there is no cold person-to-person messaging, which removes the spam-and-scam broadcast vector and keeps rules simple. **The 6-digit student ID is PII and is never exposed anywhere** — profiles show a display name derived from the address (initial + surname), and the ID itself exists only inside the UM Address at signup.

Photos are embedded in the Listing document per ADR 0006, so the model needs no Storage bucket or storage rules in v1. The model is deliberately flat: no subcollections beyond chat messages, no joins, no aggregation pipelines — pilot-scale reads stay comfortably inside Spark quotas, and the invariants that matter (rating eligibility, chat participants, admin-only reports) are enforced by security rules rather than application code.
